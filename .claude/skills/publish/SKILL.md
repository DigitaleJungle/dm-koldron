# Publish: promote an existing tag to a Windows release

A Git tag is **not** automatically a GitHub Release. Publish only the selected existing version, and include **all Added, Changed and Fixed changelog entries from every version since the previous published GitHub Release**. Build and verify on the user's Windows machine, not GitHub Actions.

1. **Select and validate a tag.** Accept optional `/publish vX.Y.Z`; otherwise use the **newest** `vX.Y.Z` tag in the repository (highest version, by `git tag --sort=-v:refname`), even when `HEAD` has moved on since. Validate the tag format and uniqueness, its commit, remote/repository, `gh auth status`, and that `gh release view vX.Y.Z` does **not** already exist. A GitHub API/permissions/network failure is **not** evidence that a release is absent: stop on such errors. Confirm the selected tag exists remotely; push that exact tag only when explicitly needed and safe. No force push. Do not change versions, write commits or create tags.
2. **Check for a local build of that version first.** Look in the user's checkout at `src-tauri/target/release/bundle/` (`nsis/`, `msi/`) for installer(s) of exactly `X.Y.Z`. Reuse them, and skip the worktree build of steps 3 and 4, only when **all** hold: the installer's file name carries `X.Y.Z`; its `.sig` is beside it and not empty; the installer was written after the tag's commit time (`git log -1 --format=%cI vX.Y.Z`); and no source file changed between the tag and the commit checked out when it was built, so `git diff --quiet vX.Y.Z HEAD -- src src-tauri/src src-tauri/Cargo.toml src-tauri/tauri.conf.json package.json package-lock.json` passes **and** the working tree is clean. If any check fails, or it's unclear, say which one and build as below; never publish an artifact whose origin is uncertain. When reusing, still run `npm run verify` on the tag (in a worktree at the tag, or in the checkout when it's at the tag) and still apply step 5's checks to the reused files. Say in the preview (step 7) that the installers were reused and when they were built.
3. **Build from exactly that tag.** Require the working tree to be clean; avoid changing the user's checkout when publishing an older tag by using a disposable `git worktree` at the selected commit (outside the active working directory). Use that worktree for all subsequent commands and read `package.json` there; verify its version equals `X.Y.Z` and Tauri/Rust versions agree. Track and clean up only the temporary worktree created by this operation.
4. **Verify locally.** Confirm Windows tooling, Rust, Node, GitHub CLI, dependencies and required secrets/signing config are available. In the tagged worktree run the project's documented deterministic dependency installation (`npm ci` when a lockfile is present), `npm run verify`, then `npm run tauri build`. Stop on errors. No GitHub Actions and no cloud build fallback. After step 5's checks pass, copy the verified installer(s) and their `.sig` files into the user's checkout at `src-tauri/target/release/bundle/<format>/` (git-ignored, replacing older files of the same name only), before the worktree is removed, so a later run can reuse them (step 2).
5. **Verify installer outputs.** Discover the *actual* files created in `src-tauri/target/release/bundle/` (MSI and/or NSIS depending on config); ensure at least one expected Windows installer exists and its version matches `X.Y.Z`. Do not require both formats unless configured. Reject stale, mismatched or empty artifacts. Don't make a `SHA256SUMS.txt`: GitHub shows each asset's SHA-256 itself. **The app updater is configured** (`plugins.updater` in `tauri.conf.json`, `createUpdaterArtifacts: true`): the build needs `TAURI_SIGNING_PRIVATE_KEY` set to the key file path (`~/.tauri/koldron.key`) or its contents (and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` if the key has one; never print, log or commit the key). Stop if the key is missing, and check every installer has its `.sig` beside it. Don't upload the `.sig`: its contents go into `latest.json` (step 8), the only place the updater reads it. Never publish an unsigned update manifest.
6. **Find the previous published release.** Query GitHub Releases, **not Git tags**, excluding drafts and normally excluding prereleases when publishing stable versions. From published releases whose tags are ancestors of the selected version, choose the nearest predecessor by Git ancestry / version, not simply the first item returned by a date-sorted `gh release list`. If history is ambiguous (diverged branches, gaps, missing changelog), stop and ask instead of silently omitting changes. The first release has no predecessor.
7. **Aggregate complete release notes.** Read `CHANGELOG.md` **at the selected tag**. Include entries for every version in `(previous_published_version, selected_version]`, including versions with tags but no GitHub Release; for a first release, include every version section through the target. Combine all `### Added` entries into **Added**, `### Changed` into **Changed**, and `### Fixed` into **Fixed**, newest first within each group, preserving every meaningful change (do not summarize away entries). Optionally prefix entries with their source version for traceability. Add a concise intro and a link to the previous release comparison if appropriate. Do not include changes after the selected tag. Show a preview of notes and chosen installer assets before publication; request approval for this irreversible public action.
8. **Publish using local artifacts.** Write release notes to a UTF-8 temporary file to avoid shell quoting/length problems. Create a GitHub Release with `gh release create vX.Y.Z --verify-tag --title "Koldron vX.Y.Z" --notes-file <file> <explicit-path-to-installer> ...`. The release's assets are the installer(s) and `latest.json`, nothing else. Prefer a **draft release** while assets are uploaded/validated, then publish it after confirming that the notes/assets are correct. While it's a draft, write the update manifest `latest.json` (UTF-8): `{"version":"X.Y.Z","notes":"<short intro>","pub_date":"<RFC 3339 now>","platforms":{"windows-x86_64":{"signature":"<the installer's .sig file contents>","url":"<the installer's browser_download_url, read from the draft's assets with `gh release view vX.Y.Z --json assets`, since GitHub renames file names>"}}}`, upload it, and check that its url matches the uploaded asset. Installed apps read it from `releases/latest/download/latest.json`, so a release without it (or a pre-release) offers no update. Do not upload unapproved or unrelated artifacts; do not force overwrite an existing release.
9. **Verify and report.** Run `gh release view vX.Y.Z --json url,isDraft,assets` and confirm it is published with the expected assets. Report GitHub URL, version, installer formats (built now or reused from a local build, with its date), included change range, and successful local test/build results. If release publication or upload fails, report any partial draft state and safe resume instructions; do not repeat the version bump or create another tag.

## Rules
- Publishing does not mutate source code or version numbers.
- Never use `--no-verify`, force-push, recreate version tags, or pretend a GitHub Release is the same as a Git tag.
- Keep local builds and test execution on the user's own Windows device. GitHub is used only for repository/tag metadata and hosting the final Release/assets.
- If publishing older versions, read changelog/build config from the selected tag, never from the currently checked-out branch.
- Do not require GitHub Actions, macOS, Linux or signing until explicitly configured; Windows-only installers are acceptable.
