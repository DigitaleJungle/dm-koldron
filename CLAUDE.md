# DM's Koldron

Koldron is an open-source (MPL-2.0), local-first desktop companion for Dungeon Masters running in-person D&D sessions. Its v1 scope includes a readable SRD 5.2 library and catalog, global search, campaigns, characters, and encounters (prepare and run). Keep the core small; community content packs extend the data, and code plugins are a later phase.

## Product specification

- `docs/SPEC.md` is the source of truth for product behavior, features, and workflows. It is local only (`docs/` is Git-ignored). Read the relevant sections before building or modifying a feature or screen.
- Follow established implementation and design patterns for details the spec does not define. Make small, reversible implementation decisions without interrupting the user.
- Ask before introducing functionality, changing user-facing behavior, making irreversible data decisions, or contradicting the spec. Do not invent features or workflows.
- When an approved decision changes behavior, update `docs/SPEC.md` as part of the same task. Do not silently rewrite the spec to justify an implementation.
- This is a rebuild of the author's private app, "Masters Companion". It is a read-only reference: selectively reuse suitable code, but never modify that repository.

## Technology stack

- Tauri 2 with a Rust backend.
- SvelteKit using Svelte 5 runes, TypeScript, Vite, static adapter, and SPA mode.
- npm is the package manager.
- Targets: Windows and macOS. UI language: English only.
- Keep desktop functionality independent of the future Craft CMS account, marketplace, and licensing backend unless a feature explicitly requires an online service.

## Content packs and licensing

- **The core contains no built-in rules data.** Rules are provided by content packs (`pack.json` and JSON files following the Koldron pack schema in `packs/packs.md`).
- The SRD 5.2 pack in `packs/srd/` uses the same loading, validation, and indexing path as community packs. Do not create a special runtime path for SRD content.
- The SRD pack's `pack.json` and `encounter-budgets.json` are generated by `scripts/build-srd-pack.mjs`; its data files are the copied sources in `packs/srd/source/`, used in place (never duplicated) (see `docs/SOURCE.md`): `5e-bits/5e-srd-api`'s `packages/5e-database/src/2024/en`, plus `5e-SRD-Rules.json` and `5e-SRD-Rule-Sections.json`, converted from the SRD 5.2.1 PDF by `docs/convert_srd_rules.py` in the 2014 Rules / Rule-Sections data format used by 5e-database. The rules JSON is not currently available from the upstream source in that format.
- The repository must be self-contained for building the bundled SRD pack. Never depend on a separate checkout or on running/calling the 5e SRD API server. Do not manually edit copied/generated source data; change the transformation or authoritative source instead.
- Preserve required legal notices: use exactly the attribution specified in SRD 5.2.1 Legal Information, plus the `5e-srd-api` MIT notice, in the pack and Settings → About. Do not invent additional Wizards of the Coast attribution. Preserve any other legally required notices in included source files.
- Packs must declare a compatible schema version. Validate completely in Rust before making data available. Report and skip invalid packs; never partially load one or prevent other valid packs from loading.
- Keep pack parsing, validation, indexing, and game-rules interpretation conceptually separate. Never assume every future community pack follows D&D 5e rules beyond its declared schema and ruleset.
- Code plugins are a later development phase. Keep boundaries clear but do not build speculative plugin APIs, runtimes, licensing checks, or a marketplace before the product specification requires them.

## Domain invariants — never break

- **No hard-coded ruleset:** Monster statistics, conditions, XP tables, encounter difficulty budgets, and other rules-specific values come from content-pack data.
- **One dice engine:** All dice rolls use the shared Rust dice parser (e.g., `2d20kh1+4`) and its notation tests. Do not implement separate dice expressions in Svelte.
- **Local campaign data:** Characters, encounters, and campaign settings are stored in each campaign's folder. Save atomically after successful validation; avoid corrupt or partial writes. Persist running encounters as state changes.
- **Safe data evolution:** Never silently delete, overwrite, or migrate a user's campaign data. Use versioned, recoverable migrations and test fixtures rather than real campaign folders; obtain approval before destructive behavior.
- **SRD updates:** Download SRD data only from `5e-srd-api`'s `5e-database-vX.Y.Z` GitHub releases, not its `5e-srd-api-v…` server releases. Convert and validate an update before atomically switching to it. Keep the previous working version on failure.
- **Offline-first:** Bundled SRD content, campaign preparation, and live-session workflows must work without network access. Online account, updates, integrations, and marketplace features must not block access to locally stored campaigns.
- **Fast search:** Index and search in Rust with SQLite FTS5; never perform indexing or expensive search on the UI thread. Search should feel instant as the user types.

## Engineering principles

- Make the smallest coherent change that fully addresses the request. Avoid unrelated refactoring, defensive abstractions, premature optimization, and speculative extensibility.
- Reuse established components, utilities, and dependencies before introducing new ones.
- Before adding a dependency, explain its purpose and alternatives. Ask for approval for new runtime dependencies, large dependencies, or architectural changes. Avoid dependencies for trivial utilities.
- Put heavy file operations, parsing, indexing, and computation in Rust, not on the Svelte UI thread. Use asynchronous I/O where appropriate and blocking worker threads / `spawn_blocking` for blocking or CPU-heavy work; an `async` command is not automatically nonblocking.
- Keep the Content Security Policy in `tauri.conf.json` strict (no inline or remote scripts): pack text is untrusted and rendered as HTML. Widen it only for a real need, by the smallest source.
- Use least-privilege Tauri permissions, capabilities, and plugins. Do not expose unrestricted filesystem or command execution to the frontend.
- Use Svelte 5 runes (`$state`, `$derived`, `$props`, `$effect`) and current project conventions. Avoid introducing legacy reactive patterns.
- `src/lib/api/` is the only frontend location allowed to call Tauri `invoke` directly. Components consume typed API wrappers.
- Return typed errors from Rust and handle them deliberately. Show actionable failures to the user where appropriate; do not silently swallow errors or expose sensitive technical details.
- Keep implementation simple enough to understand and test. Prefer explicit code over unnecessary layers of wrappers and factories.

## UI design philosophy

Koldron is a focused, professional desktop tool for Dungeon Masters, not a marketing site, onboarding tutorial, or generic SaaS dashboard. Optimize for clarity, quick scanning, and efficient use during a live game.

### Purposeful interface copy

- **Every visible word must earn its place.** Labels, headings, descriptions, badges, and helper text must convey necessary information or guide an action.
- Do not add subtitles below page titles by default. Avoid welcome messages, decorative copy, introductions, filler sentences, and explanatory paragraphs in panels, cards, and dialogs.
- Do not repeat information that is already clear from the parent heading, navigation, icon with a clear label, surrounding context, or control.
- Prefer short, functional text (`Add monster`, `Difficulty`, `Save`) over instructional sentences.
- Do not add a heading to every container when grouping and layout already establish its purpose.
- Use tooltips or contextual help for secondary explanations, not permanently visible instructions. Never hide essential warnings, validation, or consequences exclusively in a tooltip.
- Preserve visible labels for ambiguous inputs and actions; never sacrifice discoverability or accessibility just to reduce text.
- Do not add badges or status labels unless they communicate a meaningful state.

### Layout and visual consistency

- Prioritize actual content and controls. Use compact, comfortable spacing with high information density, especially in live-session views.
- Avoid excessive cards, nested panels, borders, shadows, large empty areas, and oversized padding. Do not create dashboard KPI cards without a genuine user need.
- Prefer alignment, grouping, hierarchy, and typography over extra text or decoration.
- Follow approved wireframes and established navigation patterns. Do not invent a new layout pattern or redesign unrelated screens without approval.
- Reuse existing UI components and tokens before creating new variants.
- Favor restrained fantasy/alchemy personality over visual novelty that slows down the DM.
- Design for realistic data and practical desktop window sizes, not just attractive empty mockups.

### UI implementation rules

- Use tokens from `src/lib/styles/tokens.css`; do not hard-code colors, spacing, or font sizes.
- Every view must handle meaningful empty, loading, and error states, without verbose placeholder copy.
- Ensure keyboard accessibility, visible focus states, sensible accessible names, and WCAG AA contrast.
- Light/dark themes use `<html data-theme="light|dark">`. Settings → UI selects Light, Dark, or System. Do not query `prefers-color-scheme` inside components.
- Motion follows Settings → UI → Animations through `data-motion`; use `reduceMotion()` in code. Do not query `prefers-reduced-motion` directly.
- Use platform-correct shortcuts (Cmd on macOS, Ctrl on Windows). No application-wide global shortcuts unless specifically approved. `Space` advances to the next turn only when focus is not inside a text-entry or other interactive control that uses Space.
- Format dates and numbers using `Intl` and the system locale. Put user-visible UI strings in `src/lib/strings.ts`.
- Lazy-load views unnecessary for the Start screen.
- **Back:** every screen that goes back uses `src/lib/components/BackButton.svelte` (a true history back, labelled "Back", falling back to the Start screen when there is no previous place). Never add another back link or a "Back to …" label. Opening a place (tab, category, chapter, entry…) is a normal navigation (a history step); refining a list in place (search, filters, sort, page) uses `gotoReplacing`, never `goto(…, { replaceState })` or `data-sveltekit-replacestate`. Give every scrolling pane `use:keepScroll` so Back returns to its scroll position (all in `src/lib/stores/history.svelte.ts`).

### UI completion check

Before declaring a new or modified screen finished, remove redundant subtitles, descriptions, headings, badges, and helper text. Check clarity, information density, keyboard interaction, focus, resizing, and consistency with the approved wireframe. A simpler interface is the default; accessibility and clarity take precedence over minimalism.

## Development workflow

- Follow `TODO.md` (local only) as the default build order: app shell → Start screen → Settings (UI, Campaigns) → About and legal notices → SRD rules text → pack loader and SRD pack → Rules reader → Catalog → global search → campaign shell and Characters → Encounters Prepare → Encounters Run → campaign Home → community packs and Update rules.
- Do not jump ahead to unrelated features without explicit direction.
- Read relevant specification and existing components before editing. For complex, risky, or cross-cutting work, briefly outline the approach first; implement straightforward changes directly.
- For UI work, consult approved wireframes/design references before coding. If a required design decision is missing, ask; otherwise follow established patterns.
- After a change, run the type check and relevant tests. Run additional Rust checks when Rust is affected. Fix failures caused by the change before calling the task complete; report unrelated failures accurately.
- Summarize what changed, what was verified, and any remaining limitations concisely.
- Do not commit, tag, push, or publish unless the user explicitly asks.

## Model routing

- Use the `model-router` skill if installed and if delegation is useful; do not block a task if it is unavailable.
- Haiku: simple, self-contained mechanical edits, formatting, renaming, routine searches, and clear data transformations.
- Sonnet: ordinary features, UI components, bug fixes with reproduction steps, tests, and documentation.
- Opus: architecture, pack-schema decisions, subtle debugging, and cross-cutting refactors.
- Keep product decisions, planning, requests needing clarification, and trivial changes in the main session when delegating would cost more than it saves.
- Give workers specific files, relevant spec sections, constraints, and acceptance checks. Review their changes and validate with appropriate checks.

## Commits, versions, and publishing

- **Every Git commit increments the application version and receives an annotated `vX.Y.Z` Git tag.** Git tags are development milestones, not necessarily downloadable releases.
- Commit only through the `commit` skill; publish only through the `publish` skill. If a required skill is unavailable, say so rather than improvising release steps.
- Before 1.0.0: **minor** for a new functional area or screen, **patch** for all other changes. The first `1.0.0` is the finished, explicitly approved v1 core. After 1.0.0, base major/minor/patch on compatibility impact under Semantic Versioning.
- The `commit` skill determines the level from the actual changes; ask only when meaningfully ambiguous. Never create duplicate tags or overwrite published history.
- Every commit records concise, accurate user-facing Added, Changed, and Fixed entries as applicable in `CHANGELOG.md`. Update `README.md` when setup, usage, supported functionality, or project status materially changes; do not rewrite it for every minor tweak.
- **Only explicitly selected tags become GitHub Releases.** The `publish` skill builds and verifies installers locally on the target platform; it never bumps the application version.
- GitHub Release notes must consolidate **all user-facing changes since the preceding published release**, including changelog entries for intermediate tags without GitHub Releases. Do not include changes from later tags when publishing an older version.
- Verify release artifacts before uploading them. Never publish a failed or unverified build. Windows builds run locally; macOS builds require an appropriate Mac environment if/when supported.
- Never use `--no-verify`, force-push version tags, or silently skip failing checks.
