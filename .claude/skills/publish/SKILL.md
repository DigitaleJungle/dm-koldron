# Publish: promote an existing tag to a Windows release

A Git tag is **not** automatically a GitHub Release. Publish only the selected existing version, and include **all Added, Changed and Fixed changelog entries from every version since the previous published GitHub Release**. Build and verify on the user's Windows machine, not GitHub Actions.

1. **Select and validate a tag.** Accept optional `/publish vX.Y.Z`; otherwise use an exact `vX.Y.Z` tag at `HEAD`. Validate the tag format and uniqueness, its commit, remote/repository, `gh auth status`, and that `gh release view vX.Y.Z` does **not** already exist. A GitHub API/permissions/network failure is **not** evidence that a release is absent: stop on such errors. Confirm the selected tag exists remotely; push that exact tag only when explicitly needed and safe. No force push. Do not change versions, write commits or create tags.
2. **Build from exactly that tag.** Require the working tree to be clean; avoid changing the user's checkout when publishing an older tag by using a disposable `git worktree` at the selected commit (outside the active working directory). Use that worktree for all subsequent commands and read `package.json` there; verify its version equals `X.Y.Z` and Tauri/Rust versions agree. Track and clean up only the temporary worktree created by this operation.
3. **Verify locally.** Confirm Windows tooling, Rust, Node, GitHub CLI, dependencies and required secrets/signing config are available. In the tagged worktree run the project's documented deterministic dependency installation (`npm ci` when a lockfile is present), `npm run verify`, then `npm run tauri build`. Stop on errors. No GitHub Actions and no cloud build fallback.
4. **Verify installer outputs.** Discover the *actual* files created in `src-tauri/target/release/bundle/` (MSI and/or NSIS depending on config); ensure at least one expected Windows installer exists and its version matches `X.Y.Z`. Do not require both formats unless configured. Reject stale, mismatched or empty artifacts. Generate SHA-256 checksums for the exact chosen assets, ideally in a `SHA256SUMS.txt`. Include Tauri updater assets and signatures only if the updater is explicitly configured; never publish unsigned update manifests.
5. **Find the previous published release.** Query GitHub Releases, **not Git tags**, excluding drafts and normally excluding prereleases when publishing stable versions. From published releases whose tags are ancestors of the selected version, choose the nearest predecessor by Git ancestry / version, not simply the first item returned by a date-sorted `gh release list`. If history is ambiguous (diverged branches, gaps, missing changelog), stop and ask instead of silently omitting changes. The first release has no predecessor.
6. **Aggregate complete release notes.** Read `CHANGELOG.md` **at the selected tag**. Include entries for every version in `(previous_published_version, selected_version]`, including versions with tags but no GitHub Release; for a first release, include every version section through the target. Combine all `### Added` entries into **Added**, `### Changed` into **Changed**, and `### Fixed` into **Fixed**, newest first within each group, preserving every meaningful change (do not summarize away entries). Optionally prefix entries with their source version for traceability. Add a concise intro and a link to the previous release comparison if appropriate. Do not include changes after the selected tag. Show a preview of notes and chosen installer assets before publication; request approval for this irreversible public action.
7. **Publish using local artifacts.** Write release notes to a UTF-8 temporary file to avoid shell quoting/length problems. Create a GitHub Release with `gh release create vX.Y.Z --verify-tag --title "Koldron vX.Y.Z" --notes-file <file> <explicit-path-to-installer> ... <checksums>`. Prefer a **draft release** while assets are uploaded/validated, then publish it after confirming that the notes/assets are correct. Do not upload unapproved or unrelated artifacts; do not force overwrite an existing release.
8. **Verify and report.** Run `gh release view vX.Y.Z --json url,isDraft,assets` and confirm it is published with the expected assets. Report GitHub URL, version, installer formats, included change range, checksum file, and successful local test/build results. If release publication or upload fails, report any partial draft state and safe resume instructions; do not repeat the version bump or create another tag.

## Rules
- Publishing does not mutate source code or version numbers.
- Never use `--no-verify`, force-push, recreate version tags, or pretend a GitHub Release is the same as a Git tag.
- Keep local builds and test execution on the user's own Windows device. GitHub is used only for repository/tag metadata and hosting the final Release/assets.
- If publishing older versions, read changelog/build config from the selected tag, never from the currently checked-out branch.
- Do not require GitHub Actions, macOS, Linux or signing until explicitly configured; Windows-only installers are acceptable.
